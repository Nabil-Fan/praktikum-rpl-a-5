Menggunakan satu backend Laravel yang melayani dua client sekaligus — yaitu web browser untuk admin dan merchant, serta aplikasi Android Kotlin untuk user — merupakan pendekatan yang umum digunakan pada banyak startup maupun sistem production modern. Dengan satu database MySQL dan satu source code backend, pengelolaan business logic, validasi data, autentikasi, dan maintenance sistem menjadi jauh lebih sederhana dibanding harus memisahkan backend menjadi dua project berbeda. Karena itu, untuk kondisi tim pengembangan mahasiswa atau startup kecil, pendekatan satu project Laravel jauh lebih direkomendasikan dibanding membuat backend terpisah untuk web dan mobile.

Dalam implementasinya, Laravel memang sangat cocok menggunakan pemisahan route melalui web.php dan api.php. Route pada web.php digunakan untuk halaman Blade yang dipakai admin dan merchant, sedangkan api.php digunakan untuk endpoint JSON yang akan diakses aplikasi Android Kotlin. Namun, walaupun masih berada dalam satu project Laravel, controller sebaiknya tetap dipisahkan antara web dan API. Misalnya, controller seperti Web\MerchantController digunakan khusus untuk halaman Blade, sedangkan Api\FoodController digunakan khusus untuk response JSON mobile. Secara teknis sebenarnya satu controller bisa dibuat mengembalikan response berbeda tergantung jenis request, misalnya menggunakan pengecekan expectsJson(), tetapi praktik seperti itu biasanya membuat kode cepat berantakan ketika project mulai besar. Kebutuhan web dan mobile pada dasarnya berbeda: web membutuhkan redirect, session, dan view Blade, sedangkan mobile membutuhkan JSON response, status code API, token authentication, dan format response yang konsisten. Karena itu, pemisahan controller merupakan pendekatan yang jauh lebih bersih dan mudah dirawat.

Walaupun controller dipisahkan, business logic utama tetap sebaiknya dipusatkan dalam service layer agar tidak terjadi duplikasi kode. Struktur seperti Controller → Service → Model/Repository merupakan pola yang sangat baik untuk EcoEats. Sebagai contoh, proses penting seperti validasi stok surplus, checkout order, pengurangan stok makanan, atau perhitungan diskon sebaiknya ditulis satu kali saja di dalam service, lalu dipanggil baik oleh controller web maupun controller API. Dengan pola ini, ketika ada perubahan aturan bisnis, tim hanya perlu memperbaiki logika di satu tempat tanpa takut terjadi inkonsistensi antara web dan mobile.

Untuk workflow tim, sebenarnya tim Kotlin tidak perlu menunggu tim Laravel selesai terlebih dahulu. Justru praktik yang benar dalam pengembangan modern adalah backend dan mobile berjalan paralel. Hal yang paling penting di awal bukan endpoint yang sudah selesai coding, melainkan kesepakatan mengenai API contract. Tim backend dan mobile perlu menyepakati terlebih dahulu endpoint apa saja yang tersedia, method yang digunakan, struktur request, struktur response JSON, format error, dan status code yang akan dipakai. Setelah API contract disepakati, tim Kotlin sudah bisa mulai membuat UI, model data, Retrofit service, RecyclerView, dan alur aplikasi tanpa harus menunggu backend selesai.

Agar proses paralel ini lebih mudah, kalian sangat disarankan menggunakan tools dokumentasi API seperti Swagger atau OpenAPI. Dengan Swagger, tim backend dapat mendefinisikan bentuk endpoint dan response sejak awal, sehingga tim Kotlin dapat langsung memahami bagaimana API nantinya bekerja. Selain itu, untuk mengatasi masalah endpoint yang belum selesai dibuat, kalian bisa menggunakan mock API. Salah satu cara paling sederhana adalah menggunakan Postman Mock Server, Mockoon, atau JSON Server. Dengan mock API, tim backend dapat memberikan response JSON palsu sesuai format yang sudah disepakati, sehingga tim Kotlin dapat langsung melakukan testing parsing data dan pengembangan UI tanpa harus menunggu database maupun backend asli selesai dibuat. Ketika backend Laravel sudah benar-benar jadi, tim Kotlin tinggal mengganti base URL dari mock API ke server asli tanpa perlu mengubah banyak kode.

Untuk autentikasi, pendekatan yang paling cocok adalah menggunakan session authentication Laravel biasa untuk web admin dan merchant, sedangkan aplikasi Android Kotlin menggunakan token-based authentication seperti Laravel Sanctum. Sanctum cukup ringan, mudah diimplementasikan, dan memang dirancang untuk kebutuhan SPA maupun mobile API sehingga sangat cocok digunakan dalam arsitektur EcoEats.

Secara keseluruhan, arsitektur satu Laravel project dengan pemisahan web.php dan api.php, controller yang dipisahkan antara web dan API, business logic yang dipusatkan pada service layer, serta workflow paralel menggunakan mock API dan dokumentasi Swagger merupakan pendekatan yang sudah sangat baik, scalable, dan profesional untuk proyek seperti EcoEats.|
